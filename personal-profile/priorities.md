# Priority model

**Applicability:** any host that surfaces a work queue (tasks, todos, a briefing) and needs to rank items instead of listing them flat.

## Priority dimension (urgency x importance)

- **p1** — urgent + must-happen. A hard deadline, an external consequence, a cost, or a client/customer-facing request. Client-facing work always outranks internal work at the same urgency, because someone outside is waiting.
- **p2** — must-happen, no acute time pressure.
- **p3** — should-happen, no real urgency, low motivation to start.
- **p4** — want-to-happen, no pressure, but genuine interest.

## Admission dimension (commitment vs idea)

Priority alone doesn't decide whether something is a task. An item only becomes a task when *both* conditions hold: (1) someone is waiting on it or a real consequence follows from inaction, and (2) the next concrete action is known. If either condition fails, the item belongs in a knowledge/ideas layer (e.g. an ideas garden), not in the task queue — no matter how important it sounds. Mixing commitments and ideas in one list leads to queue pollution, avoidance spirals, and real commitments rotting invisibly.

## Due dates and resurface discipline

Only attach a hard `due` when there is an actual external deadline — don't invent one to create urgency. But every open task must carry either a real deadline *or* an internal resurface date (the next point at which it should be reviewed). A task without any date is structurally invisible to any filtered delivery channel (push notifications, morning briefings) and will rot. When a p1/p2 item is past a stated deadline, ask about it rather than silently re-prioritizing or dropping it.
